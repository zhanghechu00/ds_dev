下面按你这份“优化效果评估体系”里的指标，给出“在真实 Agent 使用时怎么落地计算”的做法（你现在这种工具型 Agent 最容易做到的是：运行时埋点 + 离线汇总）。

**0. 先明确数据来源（不然算不出来）**
- **会话日志**：每次用户请求、模型回复、tool_calls、tool 输出、错误、耗时、token 用量（如果 API 返回）都要记录成结构化日志（JSONL 最方便）。
- **任务口径**：什么算“一个 task”？通常可用“用户一次明确意图 + Agent 给出最终答复/完成工具链”为 1 个 task。
- **真值口径（ground truth）**：没有真值就只能做“弱评估”（LLM 打分/规则打分/人工抽检）；有真值才能做“准确率/F1/检索 recall”等硬指标。

## 1) 任务成功率指标（Task Success Metrics）

**1.1 success_rate / partial_success_rate / failure_rate**
- **最落地的计算方式（工具型 Agent 强烈推荐）**：用“状态机/事件规则”定义成功：
  - 成功（完全成功）：按业务定义的关键步骤全部完成（例如：必需工具都执行成功 + 生成了预期文件/图片链接 + 无异常）。
  - 部分成功：关键步骤完成一部分，但缺少某个后置步骤或结果不完整。
  - 失败：关键工具失败、参数缺失未补齐、或最终结果无有效输出。
- **公式**：
  - `success_rate = successful_tasks / total_tasks`
  - `partial_success_rate = partial_success_tasks / total_tasks`
  - `failure_rate = failure_tasks / total_tasks`
- **需要记录的最小字段**：`task_id/session_id`、`tool_success`、`tool_name`、`final_response_present`、`error_type`。

**1.2 completion_score（完成度 0-1）**
- **规则法（更稳）**：给每个任务定义 checklist（例如 5 个必达项），完成 4/5 就是 0.8。
- **LLM 评审法（更主观）**：把“任务要求+Agent 输出”喂给评审模型让它打 0-100。要注意一致性和偏差，建议固定 prompt、固定模型、抽样校准。

**1.3 accuracy_score（准确度 0-1）**
- 有 ground truth：用
  - **精确匹配**（严格字符串/结构字段一致）
  - **F1**（问答抽取类：按 token/关键词集合算 precision/recall）
  - **语义相似度**（embedding cosine，相对稳但要设阈值）
- 没 ground truth：退化为“引用一致性/事实可追溯”（见 RAG 的 groundedness）。

## 2) 质量指标（Quality Metrics）

**2.1 relevance / coherence / fluency / informativeness（0-1 或 0-10）**
- **最常用**：LLM-as-judge 打分（输入：用户问题/上下文 + 输出）。
- **落地建议**：
  - 只在离线评测或抽检时算（线上每次算会增延迟和成本）。
  - 固定评审 prompt + 固定评审模型 + 固定评分范围（0-10）。
  - 保存“评分理由/判定依据”，便于回溯。

**2.2 factuality_score（事实准确性）**
- 如果你有知识库（RAG），最落地的是“可追溯性评估”：
  - 抽取回答中的关键断言（claim extraction，可用规则/LLM）。
  - 对每条断言检索证据片段。
  - 判定“证据是否支持断言”（LLM 判定或规则判定）。
- **计算**：`factuality_score = 被证据支持的断言数 / 断言总数`。

## 3) 效率指标（Efficiency Metrics）

**3.1 latency（延迟）**
- **怎么测**：
  - `latency_end_to_end = t_response_end - t_request_start`
  - 也建议拆分：`llm_latency`、`tool_latency`、`retrieval_latency`
- **统计**：
  - 平均：`avg_latency`
  - 分位数：`p50/p95/p99`（对线上体验更有意义）
- **需要记录**：每次请求开始/结束时间戳；每个工具开始/结束时间戳。

**3.2 tokens_used（token 用量）**
- **最准确**：用模型 API 返回的 usage 字段（`prompt_tokens/completion_tokens/total_tokens`）。
- **没有 usage**：只能估算（用 tokenizer 估算），但不同模型 tokenizer 不同，误差会比较大。

**3.3 api_calls（API 调用次数）**
- 对你这个项目，通常指：
  - LLM 调用次数（首次 + tool 后补全）
  - 工具调用次数（tool_calls）
- 直接计数即可。

**3.4 estimated_cost（成本）**
- **有价格表**：`cost = prompt_tokens * price_in + completion_tokens * price_out`
- **没价格表**：先记录 token 和调用次数，成本后算（更稳妥）。

**3.5 throughput（吞吐）**
- 单机近似：`throughput_rps = 请求数 / 总耗时秒`
- 更实用：在固定并发下测 `max_rps` 和 `p95_latency` 是否满足 SLA。

## 4) 可靠性指标（Reliability Metrics）

**4.1 consistency_score（一致性）**
- 同一输入重复跑 N 次得到 outputs：
  - **文本相似度**：用 embedding cosine 或 ROUGE-L 的平均相似度。
  - `consistency_score = avg(sim(output_i, output_j))`（两两组合平均）
- 同时记录 `unique_outputs`（输出去重后的数量），越多表示波动越大。

**4.2 robustness_score（鲁棒性）**
- 做输入扰动（空格、同义改写、错别字等），比较输出与原始输出的相似度或任务成功率变化：
  - `robustness_score = avg(sim(output_original, output_perturbed_k))`
  - 或者更直接：`robust_success_rate = 扰动输入下成功次数 / 扰动次数`

**4.3 error_handling_rate / graceful_degradation_rate**
- 设计 edge cases（缺参、路径不存在、外部 exe 不可用、超时等）：
  - `error_handling_rate = 未崩溃并给出可理解回应的次数 / edge_cases 总数`
  - `graceful_degradation_rate = 输出包含“明确原因+下一步可操作建议”的次数 / edge_cases 总数`
- 你这种工具型 Agent 特别建议把错误分为：参数缺失/文件不存在/外部程序失败/权限/超时，并统计各自占比。

## 5) 用户体验指标（UX Metrics）

**5.1 评分类（helpfulness/clarity/completeness/satisfaction）**
- 需要前端收集 1–5 分，后端落库：
  - 平均分：`avg_x = sum(x) / n`

**5.2 NPS（净推荐值）**
- 传统 NPS 是 0–10 分；你文档里用 satisfaction(1–5)替代也可以，但要先定义映射口径。
- 标准口径（0–10）：
  - Promoters：9–10；Detractors：0–6
  - `NPS = (promoters% - detractors%) * 100`
- 若用 1–5：建议映射：5→9–10，4→7–8，1–3→0–6，再算标准 NPS。

**5.3 留存/复用率**
- `retention_rate = would_use_again 为 true 的比例`
- 或按时间窗口：7 日内回访用户数 / 当期用户数。

## 6) 检索指标（Precision@k / Recall@k / MRR / NDCG）怎么“真正算”
前提：你必须有“相关文档集合 relevant_docs”（人工标注或基准集），否则无法算真实 recall/ndcg。
- `precision@k = topk 中相关文档数 / k`
- `recall@k = topk 中相关文档数 / relevant_docs 总数`
- `MRR = 1 / rank`（第一个相关文档的排名；没有相关则 0），对多 query 取平均
- `NDCG@k`：需要每个文档的相关性等级（0/1/2…），用标准 DCG/IDCG 公式归一化

**落地建议（最关键）**
- 线上先做“可自动算”的：成功率/缺参率/工具耗时/p95 延迟/工具失败分类。
- 离线再做“需要评审或标注”的：质量分、事实性、检索 recall/ndcg、鲁棒性/一致性。
